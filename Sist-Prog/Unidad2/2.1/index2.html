Máquinas de Estados Finitos

2.1.2

Modelar el comportamiento del firmware como estados y transiciones, antes de escribir una línea de código

// El modelo

Qué es una FSM

Un modelo donde el sistema solo puede estar en un estado concreto a la vez — por ejemplo REPOSO, ARMADO o ALERTA — y únicamente cambia de estado cuando ocurre un evento específico: una condición, un tiempo cumplido o una señal externa.

Por qué formalizarla con diagramas UML

Dibujar el diagrama de estados antes de programar (círculos = estados, flechas = transiciones etiquetadas con el evento que las dispara) obliga a pensar en todos los casos posibles y evita huecos de lógica que después se convierten en bugs difíciles de rastrear.

// Cómo se lleva a firmware

Representar estados con enum class

En vez de usar números sueltos o cadenas de texto para saber en qué estado está el sistema, se define un tipo enumerado fuertemente tipado. Cada nombre de estado queda legible en el código, y el compilador evita comparaciones inválidas entre estados de distinto tipo.

Tablas de transición

Una tabla que cruza "estado actual" contra "evento recibido" y da como resultado el "estado siguiente" es la forma más clara de documentar todas las reglas del sistema antes de programar, y sirve como referencia directa para depurar cuando el comportamiento no es el esperado.

Ejemplos típicos

Un semáforo vehicular y peatonal, una alarma de seguridad con clave de acceso, o el control de un electrodoméstico son casos donde formalizar la FSM antes de codificar ahorra horas de depuración y hace el firmware predecible.
